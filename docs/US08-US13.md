## Preparación y arranque

Usar Node >=22 (la instalación verificada usa Node 24), PostgreSQL y Redis. Resend ya estaba integrado y la clave local existente se reutiliza. En desarrollo se conserva el remitente de pruebas `onboarding@resend.dev` cuando no se configura RESEND_FROM; para producción se requiere un remitente configurado.

```powershell
npm ci
npm run db:generate
# Aplicar sobre la base correspondiente al entorno de ejecución, después de revisar su URL:
npm run db:migrate:deploy
# Redis local opcional si tenés Docker:
docker compose -f compose.receipts.yml up -d
npm run dev
# En otra terminal, mantener este proceso en ejecución:
npm run worker:receipts
```

Conservar la RESEND_API_KEY existente y agregar la configuración de cola en `.env` o `.env.local`:

```dotenv
MOSTRADOR_BRANCH_NAME="Bahía Blanca"
REDIS_URL="redis://127.0.0.1:6379"
# RESEND_API_KEY ya configurada: se reutiliza.
# Opcional en local; configurar remitente con dominio verificado para producción:

# Para registrar eventos de entrega/rebote; no es requisito del envío:
RESEND_WEBHOOK_SECRET="<secreto de firma del webhook>"
```

Se mantienen las conexiones PostgreSQL, las claves Clerk y la cuenta Resend existentes. No versionar secretos. El remitente de pruebas conserva las restricciones de destinatarios de Resend. Para observar entregas y rebotes, suscribir en esa misma cuenta los eventos `email.delivered` y `email.bounced` a `/api/webhooks/resend`. La firma se verifica sobre el body original con Svix; eventos adelantados al registro local responden 503 para que el proveedor reintente. Sin webhook, se puede enviar y registrar aceptación, pero no confirmar entrega mediante eventos.

## Venta en Mostrador

- Abrir `/mostrador` con una sesión MOSTRADOR o ADMIN. Hay accesos desde el encabezado del panel y del sitio para personal autorizado.
- Al iniciar sesión, MOSTRADOR abre directamente `/mostrador`; ADMIN sigue entrando al panel y PASAJERO al buscador. Esto no restringe la navegación posterior del empleado. El encabezado de mostrador sigue WF-08 e integra el avatar/menú de Clerk para cerrar sesión.
- Buscar origen/destino/fecha, elegir tarifa y registrar 1 a 9 viajeros. DNI de 7-8 dígitos; nombre/apellido con letras; teléfono de 8-15 dígitos; email del comprador válido.
- Los errores de validación aparecen debajo del campo correspondiente, en español y por pasajero, con foco en el primer dato inválido. Los rechazos de validación de la API se ubican de la misma forma. Al editar se limpia el aviso del campo; errores de disponibilidad o conexión conservan un aviso general.
- La confirmación de caja se registra con CASH, DEBIT_CARD o CREDIT_CARD. No se capturan datos de tarjeta ni se invoca la pasarela mock web para ventas presenciales.
- Asignación automática sin recargo. Elección manual en Economy con recargo por pasajero, configurado en `Fare.seatSelectionFee`. Configurarlo con la API de tarifas existente: `PATCH /api/fares/{id}` (ADMIN), body `{ "seatSelectionFee": 9800 }` como ejemplo, no como precio universal. Si el valor es cero, la terminal permite sólo asignación automática en Economy.
- La tarifa `ECON-FLEX` / Economy Premium comparte cabina física ECONOMY en el catálogo existente. Se reconoce como clase comercial Premium: no se cobra selección. Primera también incluye selección.
- El total lo calcula el servidor con Decimal; se compara nuevamente al emitir. Si cambió el precio, la terminal muestra el error y cotiza otra vez para que el operador confirme el nuevo total.
- Reserva, descuento de cupo, asientos, pago, dos comprobantes y outbox se confirman juntos. Un fallo de persistencia revierte todo. Redis o Resend no intervienen en esa transacción.
- La clave UUID `requestId` identifica el intento. Mismo operador y payload devuelven la venta ya emitida; un payload distinto con la misma clave produce 409. Ante timeout o 5xx se bloquean las ediciones hasta reintentar la misma solicitud, para consultar su resultado sin duplicar cobro.
- Al vender se muestra el mensaje literal de éxito, código visible de seis caracteres, descarga e impresión de pasaje/factura y aviso de envío encolado. Las URLs conservan el código canónico `AG-XXXXXX` para compatibilidad. La impresión abre el visor PDF y el diálogo del navegador; si el navegador impide la impresión automática, usar el botón de imprimir del visor.
- Ante conflicto de asiento se conserva el formulario y se actualiza el mapa/cotización. La web y Mostrador comparten inventario. Las pantallas abiertas se refrescan al recuperar el foco; una nueva consulta lee disponibilidad después del commit, sin caché.

## API

| Método y ruta | Entrada / resultado |
| --- | --- |
| POST `/api/v1/mostrador/cotizacion` | `{ flightId, fareId, passengersCount: 1..9, seatMode: "AUTO" o "MANUAL" }` -> `{ baseAmount, seatSelectionAmount, totalAmount, currency }` |
| POST `/api/v1/mostrador/ventas` | `{ requestId, flightId, fareId, quotedTotal, seatMode, passengers: [{ firstName, lastName, documentNumber, seatId? }], contactEmail, contactPhone, paymentMethod }` -> venta y email encolado; 201 nueva, 200 idempotente |
| POST `/api/bookings/{code}/payments` | Contrato de pago existente; `email` pasa a `{ status: "queued", dispatchId, message }` cuando el pago es aprobado. Pago rechazado: email null |
| POST `/api/bookings/{code}/payment-email` | Permisos existentes, pago aprobado, límite durable de un minuto; responde 202 con un nuevo despacho encolado |
| POST `/api/webhooks/resend` | Webhook firmado; actualiza entrega/rebote sin modificar la compra |

Las respuestas conservan `{ ok, data }` / `{ ok: false, error }`. Validación Zod devuelve 422 según la convención existente; 401 sin sesión, 403 sin rol, 404 inexistente y 409 disponibilidad/precio/idempotencia. Los handlers refuerzan los permisos aunque exista middleware.

## Despacho y recuperación

`EmailDispatch` es la outbox durable y la fuente de verdad. Guarda destinatario y documentos de compra como snapshot JSON versionado e inmutable. `EmailDispatchAttempt` registra intentos y finalización. Redis transporta sólo el identificador, sin datos personales.

El relay consulta pendientes cada 5 segundos y publica en BullMQ con ID estable. El worker reclama un lease en PostgreSQL, genera `Pasaje_[Codigo].pdf` y `Factura_[Codigo].pdf` reutilizando los generadores existentes y envía el HTML/texto institucional. El pasaje contiene una página por viajero/tramo, por lo que siempre se adjuntan dos archivos, incluso con varios pasajeros.

Se permiten cuatro intentos totales (inicial + tres reintentos), con esperas de 5, 15 y 30 segundos. Cada envío tiene timeout de 10 segundos y respeta Retry-After. Los errores permanentes fallan inmediatamente. La clave del proveedor y los bytes de los PDFs se mantienen iguales al reintentar, incluidos sus metadatos, para impedir duplicados por timeout después de aceptación. El presupuesto de intentos está en PostgreSQL y no se reinicia al reiniciar Node.

Estados:

- PENDIENTE: en espera, procesando con lease o esperando próximo reintento.
- ENVIADO: el proveedor aceptó el correo. `acceptedAt` y `providerMessageId` registran ese hecho.
- FALLIDO: error permanente o presupuesto agotado. La compra sigue PAID y los PDFs siguen descargables.
- `deliveredAt` registra entrega al servidor destinatario; `bouncedAt` registra rebote. Ninguno equivale por sí solo a demostrar ubicación en la bandeja principal.

Si Redis está caído, la outbox conserva trabajo y el relay lo publica al volver. Si un worker cae, el lease vence a los 90 segundos y el pendiente vuelve a procesarse. Monitorear antigüedad de PENDIENTE, FALLIDO, rebotes y workers detenidos. El reenvío autorizado crea otro despacho con el snapshot actual; verificar/corregir el email de la reserva antes de reenviar un rebote.

El SLA solicitado es llegada a inbox <=180 segundos en el 100% de los envíos. La implementación registra compra/encolado/aceptación/entrega para medirlo, pero no puede garantizar bandeja principal ni entrega bajo una caída prolongada del proveedor. Las tres compras sintéticas enviaron correos reales, aceptados por Resend en 7,5, 9 y 6,4 segundos desde el encolado. El destinatario confirmó recepción de los primeros dos con sus PDFs, sin una hora exacta de llegada; por eso no se afirma cumplimiento del SLA de inbox. Aceptación no demuestra entrega.

No ejecuta resets ni migra public. Necesita permiso de creación de schemas. No ejecutar el archivo de tests de base directamente: rechaza conexiones sin el namespace temporal comprobado.

Cobertura: idempotencia y payload distinto, última plaza web/Mostrador, dos asientos por último cupo, conflicto literal, recargos por clase comercial, rollback total si falla outbox, limpieza concurrente de vencimientos, snapshot inmutable, pago web y worker concurrente. Las pruebas locales cubren además firmas de webhook, errores permanentes/transitorios, reintentos, lease, caída de Redis y payload PDF determinista.

La interfaz se revisó inicialmente con componentes reales y APIs simuladas en navegador (escritorio y móvil, hasta nueve viajeros). Las pruebas PostgreSQL usan servicios reales en un namespace aislado. Después se ejecutaron ventas sintéticas con la base configurada, Redis/BullMQ real y Resend real; ver [verificación local](VERIFICACION-LOCAL-US08-US13.md). Se corrigió un timeout de descarga demasiado corto observado en esa prueba. El usuario confirmó recepción de los primeros dos correos con sus adjuntos; no se midió su hora exacta de llegada.

Los fallos previos de TypeScript y tests se corrigieron: prop `onReprogrammed`, test del horizonte anual en el servicio correspondiente y permisos de rutas explícitos por método.
